# 《悬浮时钟》跨平台版本调研报告

> 版本：v1.0 ｜ 日期：2026-10-02 ｜ 状态：待确认
> 背景：现有 iOS 版悬浮时钟 App，计划新增 **HarmonyOS（鸿蒙）** 与 **Android** 版本。本文档为开发前的平台可行性、竞品与风险调研。

---

## 1. 结论速览（TL;DR）

| 事项 | 结论 |
| --- | --- |
| Android 版可行性 | ✅ 成熟。`TYPE_APPLICATION_OVERLAY` 系统悬浮窗 + 前台服务保活，是国内非常成熟的方案，大量同类 App 已验证 |
| 鸿蒙版可行性 | ✅ 可行。HarmonyOS NEXT 提供 `window.createWindow(TYPE_FLOAT)` 系统级悬浮窗，`ohos.permission.FLOAT_WINDOW` 为用户授权权限，三方 App 可申请（已上架的「小羊时钟」等 App 验证了通路） |
| 最大的技术风险 | ⚠️ **鸿蒙后台保活**：应用退后台后进程会被挂起，悬浮窗每秒刷新依赖进程存活，而长时任务类型中没有「纯计时」类目，需首周 Spike 验证（详见 §4.3 与《03-技术方案设计》） |
| 市场判断 | Android 端为红海（同质化严重），鸿蒙 NEXT 端竞品极少，**先发窗口明显**；差异化机会：实况窗倒计时、服务卡片、跨端体验一致 |
| 相比 iOS 版的优势 | iOS 受系统限制只能用「画中画(PiP) hack」实现全局悬浮，存在审核风险；Android/鸿蒙有原生悬浮窗能力，体验更自然、可实现真·任意界面悬浮 |

## 2. 原参照：iOS 悬浮时钟类 App 的功能与实现方式

### 2.1 实现原理（为何 iOS 版做起来很"拧巴"）

iOS 没有类似 Android 的全局悬浮窗权限。市面上的 iOS 悬浮时钟（提词器、电池助手同理）几乎都基于 **画中画（`AVPictureInPictureController`）**：把时间渲染成视频帧循环播放，借助后台播放会话让 PiP 小窗在退出 App 后仍显示（参考 [float_timer_swift 开源项目](https://github.com/liu0527aa/float_timer_swift)、[自定义画中画悬浮窗实现](https://blog.csdn.net/m0_59449563/article/details/118031905)、[iOS 画中画浮窗详解](https://morganwang.cn/2022/08/16/iOS%E7%94%BB%E4%B8%AD%E7%94%BB%E6%B5%AE%E7%AA%97%E8%87%AA%E5%AE%9A%E4%B9%89)）。该方案的固有问题：样式受 PiP 窗口限制、滥用 PiP 展示非视频内容有**被 App Store 审核拒绝的风险**、视频播放结束小窗会关闭。

**对双端移植的含义**：Android/鸿蒙版本不背这些历史包袱，可以做出比 iOS 版更完整的悬浮体验（自由拖放、多点触控、贴边吸附、多悬浮窗并存）。

### 2.2 iOS 同类 App 主流功能盘点（作为产品功能基线）

对 App Store 主流产品（[悬浮时间](https://apps.apple.com/gy/app/id1568931280)、[桌面悬浮时钟](https://apps.apple.com/us/app/id6479939612)、悬浮时钟-专业计时神器等）的功能盘点：

- **核心**：实时时钟（时:分:秒，可选毫秒）、正计时秒表（计次）、倒计时（到点提醒）
- **悬浮交互**：拖动、贴边、大小/透明度/颜色/字体调节、半透明胶囊背景
- **场景**：考试控时、抢购秒杀对时、烹饪、运动、停车计费
- **扩展**：桌面/锁屏小组件、灵动岛显示、番茄钟、倒数日、翻页时钟、系统监控（网速/CPU）
- **变现**：高级样式付费、去广告订阅

## 3. 竞品格局

### 3.1 Android：红海，功能趋同

| 竞品 | 渠道 | 特点 |
| --- | --- | --- |
| 悬浮时钟（com.maoying.clockdesktop） | [小米应用商店](https://app.xiaomi.com/details?id=com.maoying.clockdesktop) | 任意界面悬浮、毫秒级、抢购对时，装机量大 |
| 悬浮时钟-计时器&倒计时（com.github.xckevin927.android.floattimer） | [Google Play](https://play.google.com/store/apps/details?id=com.github.xckevin927.android.floattimer) | 正计时+倒计时+秒杀助手 |
| FloatingClock（com.hzjuzhi.clock） | 应用宝 | 卡点抢购主打 |
| 桌面时钟助手 | 应用宝专题 | 高颜值、半透明悬浮 |

**判断**：Android 端技术门槛低、竞品密、用户对"广告多/要权限/费电"抱怨集中（各应用商店评论区高频反馈）。切入策略：**干净无广告 + 省电 + 深度 OEM 权限引导**。

### 3.2 鸿蒙 NEXT：近乎空白，先发窗口

- HarmonyOS NEXT（5.0 起"纯血鸿蒙"）**不再兼容 Android APK**，Android 上的成熟悬浮时钟全部无法直接运行，需要原生重写 → 存在明确的供给真空。
- 目前应用市场上该类目可见的主要是 **[小羊时钟](https://blog.csdn.net/2501_91974903/article/details/166141529)**（免费，模拟/数字/翻页/文字/双钟样式，桌面+悬浮），功能偏向"桌面美化时钟"，**计时工具属性（秒表/倒计时/计次/提醒）偏弱**。
- 系统自带「时钟」App 有秒表/计时器，但**无悬浮窗**，考试/抢购/烹饪场景覆盖不了。

**判断**：鸿蒙版以"计时工具 + 悬浮窗"为核心切入，配合鸿蒙特色能力（**实况窗倒计时、锁屏胶囊、服务卡片**）做出系统级差异，是本项目的最大机会点。

## 4. 平台技术可行性

### 4.1 Android：系统悬浮窗 + 前台服务（成熟方案）

| 项 | 要点 |
| --- | --- |
| 悬浮窗 API | `WindowManager.addView()` + `LayoutParams.TYPE_APPLICATION_OVERLAY`（Android 8.0/API 26+；更低版本用 `TYPE_PHONE`，2026 年可放弃） |
| 权限 | `SYSTEM_ALERT_WINDOW`（特殊权限，不可运行时弹窗申请）：`Settings.canDrawOverlays()` 检测 → 跳 `ACTION_MANAGE_OVERLAY_PERMISSION` 引导用户手动开 |
| 进程保活 | 前台服务（`startForegroundService` + 常驻通知）；Android 14（API 34）起必须声明 `foregroundServiceType`，计时类 App 采用 `specialUse`（Google Play 需在后台声明表说明用途；国内商店无此申报环节） |
| 计时精度 | 用 `SystemClock.elapsedRealtime()` **时间戳差值**驱动显示，而非累加 tick，天然免疫后台/休眠漂移；毫秒模式用 `Choreographer`/短周期 Handler |
| 倒计时到点 | 前台服务内触发；兜底用 `AlarmManager` 精确闹钟（`SCHEDULE_EXACT_ALARM`/`USE_EXACT_ALARM`）+ 通知/铃声/振动 |
| 国产 ROM 适配 | 除 AOSP 悬浮窗开关外：MIUI/HyperOS「后台弹出界面」「自启动」、OPPO/vivo 各自的悬浮窗与后台管理开关、电池优化白名单——需内置分厂商引导页 |
| 参考 | [Android 悬浮窗开发（权限+前台服务+通知）](https://blog.csdn.net/shulianghan/article/details/145711277)、[应用外悬浮窗全解析](https://comate.baidu.com/zh/page/is9o01rh6ca) |

### 4.2 鸿蒙：ArkTS 系统悬浮窗（可行，注意权限名）

| 项 | 要点 |
| --- | --- |
| 悬浮窗 API | `window.createWindow()` + `window.WindowType.TYPE_FLOAT`；`setUIContent` 加载 ArkUI 页面、`moveWindowTo`/`resize`、`setWindowBackgroundColor('#00000000')` 透明底、`destroyWindow` 销毁 |
| 权限（关键） | **`ohos.permission.FLOAT_WINDOW`**：用户授权（user_grant），三方 App 可用，`module.json5` 声明（reason+usedScene）+ `requestPermissionsFromUser()` 弹窗申请。⚠️ 不要与 `ohos.permission.SYSTEM_FLOAT_WINDOW` 混淆——后者是 ACL 受限权限（system_basic，普通 App 申请报错），网上旧教程（API 9 时代）多用后者，属过时信息 |
| 拖拽 | 悬浮窗内容页绑定 `PanGesture`，`onActionUpdate` 中 `moveWindowTo`；注意 vp/px 单位换算（vp2px） |
| 桌面卡片 | FormExtensionAbility 服务卡片（时钟/倒计时卡片） |
| 实况窗 | Live View Kit：锁屏/状态栏/通知中心的实时倒计时胶囊，HarmonyOS 6 起支持倒计时到 0 端侧自动更新——**iOS/Android 都给不了的体验** |
| 参考 | [鸿蒙 Next ArkTS 悬浮窗实现](https://bbs.itying.com/topic/68f97b8f89629100479db6b6)、[鸿蒙悬浮窗开发实战](https://www.cnblogs.com/mau123789/p/18202816)、[悬浮窗合规开发（华为云）](https://bbs.huaweicloud.com/blogs/479600) |

### 4.3 ⚠️ 鸿蒙最大风险点：退后台进程挂起 vs 每秒刷新

- HarmonyOS 的资源调度会在应用退后台后（宽限期后）**挂起进程**，`setInterval` 停止；而悬浮窗需要每秒走字（参考 [InfoQ：后台倒计时精准控制实践](https://xie.infoq.cn/article/2684d9e3c8191f5f59e6a8424)、[setInterval 退后台挂起案例](https://bbs.itying.com/topic/67e0c776687c4e0048a84d0b)）。
- 长时任务（ContinuousTask）类型清单（`DATA_TRANSFER / AUDIO_PLAYBACK / AUDIO_RECORDING / LOCATION / BLUETOOTH_INTERACTION / MULTI_DEVICE_CONNECTION / WIFI_INTERACTION / VOIP / TASK_KEEPING`，见[官方长时任务文档](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/continuous-task)）中**没有"纯计时"类目**；`TASK_KEEPING` 仅对 PC/2in1 或 ACL 应用开放（手机端三方不可用）；滥用 `audioPlayback` 等类目挂羊头卖狗肉有**上架审核风险**。
- **已知可行的工程策略**（业界实践 + 竞品验证，因「小羊时钟」等悬浮时钟确实在正常运作）：
  1. **时间戳差值计算**：任何时刻恢复渲染立即显示正确时间，不依赖连续 tick；
  2. 悬浮窗本身是"用户可感知行为"，配合合适的长时任务类目申报（以实际审核结果为准）；
  3. 倒计时到点提醒走 **`reminderAgentManager` 代理提醒**（系统级，不依赖进程存活）；
  4. 引导用户在最近任务中加锁/允许后台运行。
- **行动项**：此问题列为开发第一周的 **Spike 验证项**（详见《03-技术方案设计》§7），用最小 Demo 实测：退后台后悬浮窗刷新行为、被挂起的时机、各策略的实际效果。**它影响鸿蒙版的产品承诺（"能悬浮多久"），必须在动工前拿到实测数据。**

### 4.4 商店政策

| 渠道 | 注意点 |
| --- | --- |
| 华为 AppGallery | 鸿蒙版唯一分发渠道；上架需软著/企业或个人开发者认证；悬浮窗权限需在审核时演示真实用途 |
| 国内 Android 商店（小米/OV/荣耀/应用宝） | 需逐一上架；对「自启动/保活」类行为有各自检测，走前台服务+用户主动开启的合规路径没问题 |
| Google Play | `SYSTEM_ALERT_WINDOW` 属敏感权限、FGS `specialUse` 需申报——首发可不做海外 Play，后置 |

## 5. 综合建议

1. **做**：双端均可行，鸿蒙先发价值最高，建议鸿蒙版与 Android 版并行启动、共用一套产品/设计语言。
2. **产品定位**：「干净的悬浮计时工具」——时钟/秒表/倒计时为核心，样式美观可定制，无广告少权限；鸿蒙版叠加实况窗+服务卡片。
3. **风险前置**：鸿蒙后台保活 Spike 放在第一周；Android 的 OEM 权限引导做成可云端配置的数据。
4. **明确不做（v1）**：系统监控（网速/CPU）、云端同步、Pad/手表/PC 多端——控制范围。
