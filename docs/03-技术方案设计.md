## 1. 总体架构

两个平台独立原生开发，共用同一套**产品逻辑模型**与**设计规范**（颜色/字号/交互术语对齐《高保真原型》）。

```
┌─────────────── 共享层（各自实现，语义一致） ───────────────┐
│  计时引擎（时间戳驱动，状态机：Idle/Running/Paused/Done）      │
│  样式模型（大小/透明度/颜色/背景/显示元素，序列化到本地）        │
│  权限引导流程（步骤状态机 + 分厂商跳转配置，配置可云端热更）      │
└──────────────────────────────────────────────────┘
        │ Android                          │ HarmonyOS
┌───────┴────────────┐          ┌──────────┴─────────────┐
│ Kotlin + Compose    │          │ ArkTS + ArkUI (Stage)   │
│ OverlayWindow(FGS)  │          │ TYPE_FLOAT 悬浮窗        │
│ WindowManager View  │          │ window.createWindow      │
│ AlarmManager 兜底   │          │ reminderAgent 兜底       │
│ Glance/RemoteViews  │          │ FormExtensionAbility    │
│ (小组件 P1)         │          │ 服务卡片 + LiveView (P1) │
└────────────────────┘          └─────────────────────────┘
```

**计时引擎统一原则（双端一致）**：
- 显示值永远由「目标时刻 − 当前单调时钟」计算，**绝不累加 tick**——进程被冻结/休眠后恢复即正确；
- Android 用 `SystemClock.elapsedRealtime()`；鸿蒙用同语义单调时钟；
- 刷新调度按秒边界对齐（下一次 `xx.000` 触发），避免固定间隔漂移；毫秒模式用帧回调（`Choreographer` / ArkUI `onFrame`）。

## 2. Android 端设计

### 2.1 技术选型

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 语言/框架 | Kotlin，单 Activity + Jetpack Compose | 主流、开发效率高 |
| minSdk / targetSdk | 26 / 35 | API 26 起原生 `TYPE_APPLICATION_OVERLAY`，无需兼容旧 TYPE_PHONE |
| 悬浮窗视图 | 传统 View 体系（`FrameLayout` + `TextView`） | 悬浮窗走 `WindowManager`，Compose 需额外挂生命周期，传统 View 更稳、内存更省 |
| 存储 | DataStore（设置）+ Room（记录，P1） | — |
| 分发 | 国内 5 商店 + 官网 APK；Play 后置 | 调研报告 §4.4 |

### 2.2 模块划分

```
app/
├── ui/            Compose 界面（首页/样式/设置/权限引导）
├── overlay/       悬浮窗核心
│   ├── FloatWindowManager   addView/removeView/updateViewLayout、多实例
│   ├── FloatClockView       时钟/秒表/倒计时三种渲染（同一 View 换态）
│   └── TouchController      拖动（含边缘吸附）、单击/双击/长按手势分发
├── service/       TimerForegroundService（specialUse FGS + 常驻通知）
├── engine/        计时引擎（时间戳状态机，纯 Kotlin，可单测）
├── alarm/         AlarmManager 精确兜底 + 到点铃声/振动/通知
├── boot/          开机自启 BroadcastReceiver（默认关）
└── vendor/        分厂商权限引导配置（JSON 内置 + 远端可更）
```

### 2.3 关键实现点

**悬浮窗添加**（`TimerForegroundService` 内，确保进程活着）：

```kotlin
val params = WindowManager.LayoutParams(
    WRAP_CONTENT, WRAP_CONTENT,
    WindowManager.LayoutParams.TYPE_APPLICATION_OVERLAY,   // API 26+
    WindowManager.LayoutParams.FLAG_NOT_FOCUSABLE
        or WindowManager.LayoutParams.FLAG_LAYOUT_NO_LIMITS,
    PixelFormat.TRANSLUCENT
).apply { gravity = Gravity.TOP or Gravity.START; x = savedX; y = savedY }
windowManager.addView(floatClockView, params)
```

**权限流**：`Settings.canDrawOverlays()` → 未授权则跳 `ACTION_MANAGE_OVERLAY_PERMISSION`（带 `package:` uri 直达本应用）；返回 `onResume` 复检。通知权限（13+）运行时申请。Android 14+ 启动 FGS 时带 `foregroundServiceType = SPECIAL_USE` 并在 manifest 声明 `FOREGROUND_SERVICE_SPECIAL_USE` + `PROPERTY_SPECIAL_USE_FGS_SUBTYPE`（值：`timer_overlay`）。

**倒计时到点双保险**：FGS 内存活（正常路径）+ `setExactAndAllowWhileIdle()` 闹钟（进程被杀兜底）；二者幂等（以引擎状态机为准，防重复提醒）。

**OEM 适配**（`vendor/` 配置驱动）：按 `Build.MANUFACTURER` 映射各家额外开关的设置页 `Intent` 与文案：小米（自启动、后台弹出界面、无限制省电策略）、OPPO（悬浮窗通知、应用速冻）、vivo（后台高耗电、锁屏显示）、荣耀/华为老款（应用启动管理→手动管理）、三星（电池不受限）。尝试 `Intent` 直达，失败降级为图文引导 + 复制包名。

**省电策略**：秒级刷新用对齐 Handler（单次 UI 更新 ~1ms，功耗主要来自渲染）；息屏（`ACTION_SCREEN_OFF`）暂停刷新并停用毫秒模式；亮屏对时恢复。

## 3. 鸿蒙端设计

### 3.1 技术选型

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 语言/框架 | ArkTS + ArkUI（Stage 模型） | HarmonyOS NEXT 唯一原生路径 |
| 最低 API | API 12（HarmonyOS NEXT 5.0） | 覆盖 NEXT 存量机；实况窗特性按 6.0 做能力探测降级 |
| IDE | DevEco Studio 5+ | — |
| 存储 | `@ohos.data.preferences`（设置）+ 关系型数据库（记录，P1） | — |

### 3.2 模块划分

```
entry/
├── src/main/ets/
│   ├── pages/            首页/样式/设置/权限引导（ArkUI 页面）
│   ├── floatwindow/      悬浮窗
│   │   ├── FloatWindowController  createWindow/destroy/move/resize
│   │   └── FloatPage             悬浮窗内容（PanGesture 拖动 + 状态渲染）
│   ├── engine/           计时引擎（与 Android 同语义的时间戳状态机）
│   ├── reminder/         reminderAgentManager 代理提醒（到点兜底）
│   └── abilities/        EntryAbility（前后台切换监听、悬浮窗生命周期）
└── module.json5          requestPermissions: FLOAT_WINDOW 等
```

### 3.3 关键实现点

**悬浮窗创建与拖动**：

```typescript
import { window } from '@kit.ArkUI';

// module.json5 已声明：
// { "name": "ohos.permission.FLOAT_WINDOW",
//   "reason": "$string:float_window_reason",
//   "usedScene": { "abilities": ["EntryAbility"], "when": "always" } }

const win = await window.createWindow({
  name: 'floatClock',
  windowType: window.WindowType.TYPE_FLOAT,
  ctx: this.context            // UIAbility context
});
await win.setUIContent('pages/FloatPage');
await win.setWindowBackgroundColor('#00000000');
await win.resize(w, h);
await win.showWindow();
```

拖动：`FloatPage` 根节点绑 `PanGesture`，`onActionUpdate` 中 `moveWindowTo(px, py)`，注意 `vp2px` 换算；单击/双击用 `TapGesture(count: 1|2)` 组合。坑（来自社区实战，写进开发手册）：悬浮窗会拦截手势返回 → 悬浮窗内容必须可快速隐藏/移动；`moveWindowTo` 逐帧调用不平滑 → 用 `onActionEnd` 落点 + 位置插值。

**权限**：`atManager.requestPermissionsFromUser(['ohos.permission.FLOAT_WINDOW'])` 弹窗申请；被拒后引导 设置→应用→悬浮窗。⚠️ 文档/代码评审红线：**不得**申请 `ohos.permission.SYSTEM_FLOAT_WINDOW`（ACL 受限，三方申请直接报错，旧教程误导）。

### 3.4 后台保活策略（本方案核心风险点）

分层兜底，目标：**任何情况下倒计时到点必响；悬浮窗刷新尽力而为、恢复即准确**。

| 层 | 机制 | 说明 |
| --- | --- | --- |
| L1 显示正确 | 时间戳差值 + 前后台切换/窗口可见性恢复时立即重算 | 保证"醒来就对"，无累计误差 |
| L2 持续刷新 | 前台正常；退后台后依赖进程不被挂起 | 见下方 Spike：实测挂起时机与悬浮窗可见性的关系 |
| L3 到点必达 | `reminderAgentManager` 申请日历/闹钟类代理提醒 | 系统级执行，进程死了也响；倒计时启动时即登记，取消时撤销 |
| L4 用户协同 | 引导页：最近任务下拉加锁 + 允许后台运行提示（文案如实说明） | 不做欺骗性保活 |

**Spike-1（第一周，鸿蒙版 Go/No-Go 数据）**：真机实测矩阵——
1. 悬浮窗显示中，App 退后台：悬浮窗是否持续显示？每秒刷新持续多久后停？
2. 挂起后悬浮窗是"冻结画面"还是"消失"？
3. 声明 `audioPlayback` 长时任务（播无声/极低音量循环）后行为是否改变？→ 记录为灰区手段，**是否采用以 AppGallery 审核结果与合规评估为准**；
4. `reminderAgentManager` 到点触达率（锁屏 30min、杀进程、重启后）。
产出：实测报告 + 鸿蒙版产品承诺文案（"退后台后悬浮窗最长持续 X 分钟"或"无限制"）。

## 4. 数据模型（双端同构）

```
TimerSession { id, mode: CLOCK|STOPWATCH|COUNTDOWN, startAtMono, targetAtMono?,  // 倒计时目标时刻
               state: IDLE|RUNNING|PAUSED|FINISHED, styleId, createdAt }
StyleProfile { id, name, scale, opacity, colorToken, bgKind: CAPSULE|CARD|OUTLINE,
               showSeconds, showMillis, showDate, showWeekday, showBattery, posAnchor }
Settings { timeFormat24h, defaultStyleId, bootStart(android), screenOffPause, ringtone, vibrate, ... }
```

## 5. 状态机（计时引擎，双端一致）

```
CLOCK:     常显，无状态
STOPWATCH: Idle → Running ⇄ Paused → Idle（Reset）
COUNTDOWN: Idle → Running ⇄ Paused → Finished(提醒) → Idle
事件：start/pause/resume/reset/finish/screenOn/screenOff/processRestored
不变式：elapsed = now − startAtMono − ΣpausedDuration（恢复时以单调时钟重算）
```

## 6. 测试策略

- 引擎：单元测试（状态迁移、休眠恢复、跨天/跨时区——时区变化不影响单调时钟计时，只影响时钟显示）
- 悬浮窗：真机手工矩阵（调研 §9 场景 × 机型）+ 录屏回归
- 稳定性：Monkey 2h 无崩溃；倒计时 8h 长跑
- 鸿蒙：分布式/多窗口场景（分屏下悬浮窗行为）补充用例
